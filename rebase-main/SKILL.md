---
name: rebase-main
description: Rebase the current branch onto the latest base branch (usually `main`), resolve trivial plumbing conflicts (lockfiles, generated files) cleanly, surface real semantic conflicts, and re-run the project's verify command. Asks before force-pushing if the branch is already on the remote. Use when the user says "rebase onto main", "sync with main", or "/rebase-main".
---

Rebase the current branch onto the latest base, handle conflicts deliberately, verify the result. The user wants linear history without the foot-guns.

`ARGUMENTS` is optional — a base branch name overrides the auto-detected default branch (e.g. `/rebase-main master` or `/rebase-main develop`).

## Step 1 — Preflight

Run in parallel:

- `git status` — must be clean. If dirty, stop and tell the user to commit or stash first. Don't auto-stash; the user might be mid-thought on an unrelated change.
- `git rev-parse --abbrev-ref HEAD` — current branch. If it equals the base, stop: "Already on the base branch."
- `git rev-parse --abbrev-ref --symbolic-full-name '@{u}'` — record whether there's an upstream and what it is.
- Determine the base: use `ARGUMENTS` if set, else `gh repo view --json defaultBranchRef -q .defaultBranchRef.name`, falling back to `main`.

Fetch the latest base:

    git fetch origin <base>

Compute what's ahead:

    git log --oneline origin/<base>..HEAD

If empty, stop: "No commits to rebase."

Compute what's behind:

    git log --oneline HEAD..origin/<base>

If empty, stop: "Already up to date with origin/<base>." Nothing to do.

## Step 2 — Start the rebase

    git rebase origin/<base>

Three outcomes — handle each explicitly.

### Outcome A — Clean rebase

`git rebase` exits 0. Move to step 4.

### Outcome B — Conflicts

`git rebase` stops with conflicts. Go to step 3.

### Outcome C — Rebase fails for other reasons

(`detached HEAD`, missing commits, etc.) Surface the error verbatim and stop. Do not `git rebase --abort` automatically — the user may want to inspect the state.

## Step 3 — Resolve conflicts

For each conflicting file, classify the conflict before editing:

**Trivial plumbing conflicts** (resolve automatically, surface what you did):

- Lockfiles (`package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`, `uv.lock`, `Cargo.lock`, `Gemfile.lock`, `poetry.lock`) — accept the base side, then regenerate with the project's install command (`npm install`, `uv sync`, `cargo build`, etc.) and re-stage. Look up the install command from `AGENTS.md` / `CONTRIBUTING.md` / `package.json` scripts.
- Generated files clearly marked as such (e.g. `// @generated`, `# AUTOGENERATED`) — regenerate via the documented script.
- Pure import-order conflicts in two non-overlapping import blocks — accept both, then run the project's formatter (`isort`, `ruff`, `prettier`) on the affected file.

**Real conflicts** (surface and stop):

- Anything in source code with overlapping logic changes.
- Any conflict you're not confident about classifying.

When surfacing, list each conflicting file with the line range and your read of *why* it conflicts (e.g. "both branches renamed `foo` differently"). Then stop and pause. Do **not** continue the rebase, do **not** abort it. The user resolves and continues with `git rebase --continue` themselves.

If TodoWrite is useful (≥3 conflicting files), track each as a todo.

After resolving trivial conflicts, run `git rebase --continue` and loop. After each commit in the rebase replays, sanity-check the working tree compiles or imports cleanly if the project's check is fast (`tsc --noEmit`, `python -c "import <pkg>"`); skip if slow.

If the rebase hits another conflict mid-replay, classify again.

## Step 4 — Verify

After the rebase completes, run the project's verify command. Look it up in `AGENTS.md` / `CLAUDE.md` / `CONTRIBUTING.md`:

- Look for sections labeled "Testing", "Verification", "Pre-commit", "Build".
- Look for documented commands like `uv run pre-commit run --all-files`, `npm run lint`, `npm test`, `cargo test`, `pytest`.
- If multiple are documented (e.g. backend + frontend), run them in parallel where they don't share state.

If a verify command fails:

- Compare to the same command on the pre-rebase HEAD (`git stash`, `git checkout @{1}`, run again, `git checkout -`, `git stash pop`) — if it failed there too, the rebase didn't cause it. State that.
- If it passed pre-rebase but fails post-rebase, the rebase introduced a regression. Surface the failure verbatim and stop. Don't try to fix; that's the user's call.

If no verify command is documented anywhere, say so and stop: "No verify command documented. Suggest running tests manually."

## Step 5 — Force-push (ask first)

If the branch had an upstream (step 1) and the rebase rewrote history (`git log @{1}..HEAD` differs from `git log HEAD..@{1}`), the remote is now out of sync. Surface this and **ask** before pushing:

    Rebase rewrote history. Remote is out of sync. Push with `git push --force-with-lease`?

Do not run the force-push without confirmation. Never use bare `--force` — always `--force-with-lease` so a teammate's recent push isn't blown away silently.

If the branch had no upstream, no push action is needed; skip this step.

## Step 6 — Final report

Output a short summary:

    Rebased <branch> onto origin/<base>.
    <N> commits replayed.
    Verify: <pass/fail with command>.
    Remote: <in sync | force-push pending | no upstream>.

## Guardrails

- **Never `git rebase --abort` automatically.** If you reach a state where abort seems right, surface and ask.
- **Never `--force` without `--with-lease`.**
- **Never resolve a non-trivial conflict.** Real conflicts are surfaced for the user.
- **Never auto-stash** to start the rebase. Clean tree required.
- **Never run `git config`.**
- **Don't move on with verify failures.** A failed verify post-rebase is a real signal and stops the skill.
